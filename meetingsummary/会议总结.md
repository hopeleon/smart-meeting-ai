## 1. main.py — 主入口与管线编排

**职责**：CLI 参数解析、12 步管线编排、管线分支选择（Direct vs Map-Reduce）。

### 管线步骤

```
1. load_config()              ─ 加载配置
2. read_transcript()          ─ 读取 + 验证输入文件
3. 管线分支判断               ─ 中文字数 > 5000 → Map-Reduce，否则 → Direct
4. 摘要生成:
   Direct: call_ollama(system_prompt, transcript) → extract_json()
   Map-Reduce: split → Map(N块) → merge_deduplicate → Reduce → extract_json()
5. validate_schema()          ─ 校验顶层字段
6. --verify (可选)            ─ run_verification() → 自动修正
7. run_evaluation()           ─ 事实一致性评估（可跳过）
8. --action-items (可选)      ─ 独立行动项提取
9. run_completeness_check()   ─ 完整性检查（可跳过）
10. generate_markdown()       ─ 渲染 Markdown
11. write_output()            ─ 写 JSON + MD
12. 写各阶段辅助报告           ─ eval/actions/completeness
```

### CLI 参数一览

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `-i`, `--input` | Path | **必需** | 会议转录文本路径 |
| `-o`, `--output-dir` | Path | `output/` | 输出目录 |
| `--prefix` | str | `summary` | 文件名前缀 |
| `--skip-eval` | flag | 关闭 | 跳过事实一致性评估 |
| `--action-items` | flag | 关闭 | 开启独立行动项提取 |
| `--skip-actions` | flag | 关闭 | 明确跳过行动项提取 |
| `--skip-completeness` | flag | 关闭 | 跳过完整性检查 |
| `--verify` | flag | 关闭 | 开启二次校验+自动修正 |
| `--no-map-reduce` | flag | 关闭 | 强制跳过 Map-Reduce |
| `--no-semantic-split` | flag | 关闭 | 强制回退到说话人轮次切分 |
| `--map-reduce-threshold` | int | 5000 | 触发 Map-Reduce 的字数阈值 |
| `--chunk-size` | int | 15 | 每块说话人轮次 |

### 错误处理策略

所有辅助阶段（evaluation、verification、action_items、completeness）均采用**非阻塞降级**：`try → catch (SystemExit | JSONExtractionError | Exception) → print warning → continue`。单个辅助阶段失败不阻止摘要输出。

### 使用示例

  1. 基础用法

```bash
  python main.py -i meeting.txt
```

  行为：最简模式。自动判断文本长度：≤5000 中文字 → 直接摘要，>5000 中文字 → 语义切分 +
  Map-Reduce。事后运行事实性评估和完整性检查（均非阻塞，失败不影响输出）。

  产出文件（默认 output/ 目录）：

  ┌────────────────────────────────────┬──────────────────────────────────────────┐
  │                文件                │                   说明                   │
  ├────────────────────────────────────┼──────────────────────────────────────────┤
  │ summary_20260514.json              │ 结构化摘要 JSON                          │
  ├────────────────────────────────────┼──────────────────────────────────────────┤
  │ summary_20260514.md                │ 可读 Markdown 报告                       │
  ├────────────────────────────────────┼──────────────────────────────────────────┤
  │ summary_20260514_eval.json         │ 事实性评估报告（含分数、每条声明的判决）   │
  ├────────────────────────────────────┼──────────────────────────────────────────┤
  │ summary_20260514_completeness.json │ 完整性审计报告（议程/发言人/章节覆盖率）   │
  └────────────────────────────────────┴──────────────────────────────────────────┘

  ---
  2. 指定前缀和输出目录

```bash
  python main.py -i meeting.txt -o output/ --prefix weekly
```

  行为：与基础用法相同，但输出文件名使用 weekly 前缀，写入 output/ 目录。

  产出文件：output/weekly_20260514.json、output/weekly_20260514.md、output/weekly_20260514_eval.json、output/weekly_2026
  0514_completeness.json

  ---
  3. 跳过评估 + 行动项提取

```bash
  python main.py -i meeting.txt --skip-eval --action-items
```

  行为：与基础用法相比，不运行事实性评估（省一次 LLM
  调用），但额外运行独立行动项提取——从原文直接提取所有待办任务，做分类和优先级归一化（P0/P1/P2/P3）。

  产出文件：基础 4 文件中去掉 _eval.json，新增：

  ┌───────────────────────────────┬─────────────────────────────────────┐
  │             文件              │                说明                 │
  ├───────────────────────────────┼─────────────────────────────────────┤
  │ summary_20260514_actions.csv  │ 行动项 CSV（UTF-8 BOM，Excel 可开）  │
  ├───────────────────────────────┼─────────────────────────────────────┤
  │ summary_20260514_actions.json │ 行动项 JSON（含分类、优先级统计）    │
  └───────────────────────────────┴─────────────────────────────────────┘

  ---
  4. 自定义 Map-Reduce 阈值和块大小
```bash
  python main.py -i meeting.txt --map-reduce-threshold 3000 --chunk-size 10
```

  行为：将 Map-Reduce 触发阈值从默认 5000 字降低到 3000 字，且说话人轮次回退切分的块大小从 15 降为 10
  轮。适合想更积极触发 Map-Reduce 的场景（如 8B 小模型对中等长度文本也容易幻觉）。

  产出文件：同基础用法（4 个文件）。

  ---
  5. 开启二次校验

```bash
  python main.py -i meeting.txt --verify
```

  行为：在摘要生成后额外运行一次校验+自动修正——将摘要 JSON
  与原文逐条比对，发现不一致（人名错误、数字偏差、截止日期错误等）自动修正摘要。校验失败不阻塞管线。

  产出文件：基础 4 文件，且 summary_20260514.json 中已包含修正后的内容。控制台会打印修正数量，如 Verification: 2
  correction(s) applied.

  ---
  6. 强制跳过 Map-Reduce

```bash
  python main.py -i meeting.txt --no-map-reduce
```

  行为：无论文本多长，强制走 Direct 单次摘要管线（不切分、不 Map-Reduce）。适合 32B
  等大模型长文本直接处理能力足够、不想引入 Map-Reduce 上下文碎片化的场景。

  风险：长文本 + 小模型可能严重幻觉。仅当确认模型能处理全文时才用。

  产出文件：同基础用法（4 个文件）。

  ---
  7. 强制回退到说话人轮次切分

```bash
  python main.py -i meeting.txt --no-semantic-split
```

  行为：跳过 L1 语义切分（不调用 LLM 分析话题边界），直接走 L2 说话人轮次切分。适合以下场景：
  - 节省一次 LLM 调用（语义切分本身需要一次 API 请求）
  - 会议转录本已有清晰的说话人标签，按轮次切分效果足够好
  - 语义切分一直失败想直接走回退

  产出文件：同基础用法（4 个文件）。控制台会显示 method: speaker_turns 而非 method: semantic。

## 3. ollama_client.py — LLM 调用客户端

**职责**：统一的 LLM 调用接口，自动适配 Ollama 本地 API 和 OpenAI 兼容外部 API。

### 两种 Provider 的差异

| | Ollama | openai_compatible |
|------|--------|-------------------|
| URL | `{base_url}/api/chat` | `{base_url}{chat_path}` |
| Auth | 无 | `Bearer {api_key}` |
| Payload | `"options": {"temperature": 0.1}` | `"temperature": 0.1` |
| 响应解析 | `response["message"]["content"]` | `response["choices"][0]["message"]["content"]` |

### 关键函数

```python
call_ollama(config, system_prompt, transcript, timeout=120) -> str
```

超时/连接失败/HTTP 错误均输出英文错误信息后 `sys.exit(1)`。

## 5. chunker.py — 文本切分

**职责**：统一的长文本切分入口，三级回退策略。

### 切分策略（三级回退）

通过 `split_transcript()` 统一入口切分，按优先级依次尝试：

**L1 — 语义切分**（semantic）：调用 LLM 识别话题边界，将原文按句号/问号/感叹号/换行拆分编号后，LLM 返回起止句子编号，程序按编号切片。
- 提示词：`prompts/semantic_split_system.txt`
- 模块：`semantic_splitter.py`
- LLM 返回 `[{title, start_sentence, end_sentence, summary}]`
- 编号覆盖校验：`validate_segment_coverage()` 确保无遗漏/无重叠
- 段数限制：3-10 段
- 可通过 `--no-semantic-split` 跳过

**L2 — 说话人轮次切分**（speaker_turns）：
1. 正则 `^[一-龥]{2,4}[：:]` 匹配中文姓名（2-4 字）+ 中/英文冒号
2. 每 `max_turns`（默认 15）轮为一个 chunk
3. 相邻 chunk 重叠 `overlap_turns`（默认 2）轮，防止边界信息丢失
4. 非首个 chunk 前附会议背景（前 3 轮对话），让模型理解会议目的

**L3 — 段落切分**（paragraphs）：按空行分段（每块 ≤3000 字符），作为最终回退方案。

### 关键函数

```python
count_chinese_chars(text: str) -> int
split_transcript(transcript, max_turns=15, *, config=None, use_semantic=True) -> tuple[list[str], str]
# 返回 (chunks, method_name)，method_name ∈ {"semantic", "speaker_turns", "paragraphs"}
split_by_speaker_turns(transcript, max_turns=15, overlap_turns=2) -> list[str]
```

## 6. semantic_splitter.py — 语义话题边界切分

**职责**：调用 LLM 识别会议转录文本中的自然话题转换点，返回基于句子编号的段落划分。用于 Map-Reduce 管线的最优切分策略。

### 核心思路：句级编号定位

与旧版 marker（文本匹配）方案不同，当前版本将原文拆分为带编号的句子，让 LLM 返回起止句子编号——模型只需数句子，无需精确复制原文片段。

### 预处理流水线

```
transcript
  │
  ├─ _sentence_breaks()       → 找出所有句末位置（。！？\\n）
  ├─ _build_sentences()       → 按断句位置拆分为 span 列表 [(start,end), ...]
  └─ _build_numbered_text()   → 生成 "【1】句子一。\\n【2】句子二。" 的带编号文本
```

### 编号覆盖校验

`validate_segment_coverage(segments, total_sentences)` 确保 LLM 返回的段落划分完整无误：

| 校验项 | 规则 |
|--------|------|
| 起止顺序 | `start_sentence <= end_sentence` |
| 编号为正 | `start > 0 and end > 0`，必须为整数 |
| 首段起点 | 第一段 `start_sentence == 1` |
| 无缝衔接 | 第 N 段 `end_sentence + 1 ==` 第 N+1 段 `start_sentence` |
| 尾段终点 | 最后一段 `end_sentence == total_sentences` |

校验失败 → `ValueError` → `chunker.py` 捕获后回退到 L2 说话人轮次切分。

### 关键函数

```python
semantic_split(config, system_prompt, transcript, timeout=180) -> list[dict]
# LLM 返回 [{title, start_sentence, end_sentence, summary}, ...]
# 校验通过后才返回

locate_segments(transcript, boundaries) -> list[str]
# 根据句子编号从原文切片，返回段落文本列表

validate_segment_coverage(segments, total_sentences) -> None
# 纯函数，校验编号覆盖率，失败 raise ValueError
```

### 段数限制

3-10 段。过少（≤2）无法有效切分，过多（>10）说明切分过细，均回退。

## 7. map_reduce.py — Map-Reduce 管线

**职责**：编排 Map-Reduce 三阶段流程，专为 8B 等小模型设计。将长文本降解为多个短任务，每个都在模型能力范围内。

### 三阶段流程

#### Map 阶段 — `run_map_phase()`

```
for each chunk:
    call_ollama(map_prompt, chunk) → facts JSON
    extract_json() → {chunk_id, facts: [{type, description, source_quote, speaker, mentions}]}
```

- 顺序执行（不并发，尊重 API 速率限制）
- 单块失败 → 记录警告 + 跳过
- **全部失败** → `raise RuntimeError`（无法继续）

#### Merge 阶段 — `merge_deduplicate()`

两级去重：
1. **精确去重**：`source_quote` 完全相同 → 保留首次出现
2. **语义去重**：`description` 文本相似度 ≥ 80%（`SequenceMatcher`）→ 合并为一条

去重后按 type 分组格式化为可读文本（`_format_facts_for_reduce()`）。

#### Reduce 阶段 — `run_reduce_phase()`

```
call_ollama(summary_prompt, merged_facts, timeout=180) → 完整摘要 JSON
```

输入是去重后的结构化事实文本，**不是原始转录本**。模型只需基于已提取的事实组织摘要。

### Fact Type 分类

| type | 中文标签 | 提取内容 |
|------|---------|---------|
| `decision` | 决策 | 已做出的决策（含决策人、依据、截止时间） |
| `action_item` | 待办事项 | 待办任务（含负责人、截止日期） |
| `data_point` | 数据点 | 引用的数据（数字、百分比、日期） |
| `risk` | 风险 | 提出的风险或问题 |
| `key_info` | 关键信息 | 项目名、目标、里程碑、参与人员 |

### 关键函数

```python
run_map_phase(config, map_system_prompt, chunks, timeout=120) -> list[dict]
merge_deduplicate(facts_list: list[dict]) -> str
run_reduce_phase(config, summary_system_prompt, merged_facts, timeout=180) -> str
```

## 8. verify.py — 二次校验与自动修正

**职责**：对比摘要与原文，标记不一致并输出修正后的摘要。由 `--verify` 控制，非阻塞。

### 校验流程

```
1. _build_verify_prompt(summary, transcript)
   → "## 原始会议记录\n{transcript}\n## 待校验的会议摘要\n{summary_json}"

2. call_ollama(verify_prompt, user_prompt) → {corrections, corrected_summary}

3. _apply_corrections(original, corrected) → 安全合并
```

### 合并策略（`_apply_corrections`）

| 字段类型 | 合并方式 | 原因 |
|---------|---------|------|
| `tldr` | 非空才覆盖 | 防止空字符串覆盖有效摘要 |
| `meeting`, `next_meeting` | **浅合并**（逐字段更新） | 保留校验模型未修改的字段 |
| `discussion_points`, `decisions`, `action_items`, `issues_risks` | **整体替换**（非空列表） | 校验模型返回完整修正列表 |

### 输出结构

```json
{
  "corrections": [
    {
      "field_path": "decisions[0].deadline",
      "original": "明天",
      "corrected": "周五",
      "reason": "原文说的是周五而非周四"
    }
  ],
  "corrected_summary": { ... },
  "applied": true
}
```

### 关键函数

```python
run_verification(config, verify_system_prompt, transcript, summary, timeout=180) -> dict
```

## 9. evaluator.py — 事实一致性评估

**职责**：从摘要中提取事实声明（claim），逐一与原文比对，判定 `consistent | distorted | hallucination`。

### 评估流程

```
1. extract_claims(summary) → [{claim_id, description}]
   覆盖 meeting / discussion_points / decisions / action_items / issues_risks / next_meeting

2. _build_user_prompt(claims, transcript) → 原文 + 待检查声明列表

3. call_ollama(fact_check_prompt, user_prompt) → {verdicts: [{claim_id, verdict, reasoning}]}

4. _compile_result(claims, raw_verdicts) → 对齐 → 计算分数
```

### 对齐策略

- **claim_id 匹配**优先
- 匹配率 < 50% → **回退到位置匹配**（按数组索引）
- 无匹配 → 标记为 `error`

### 分数计算

```
factuality_score = consistent / total * 100
threshold = 95.0
```

### 判决类别

| 判决 | 含义 |
|------|------|
| `consistent` | 声明与原文完全一致，合理改写允许 |
| `distorted` | 原文涉及相关话题但具体信息（名字/数字/归因）有偏差 |
| `hallucination` | 声明在原文中**完全没有依据** |

### 关键函数

```python
extract_claims(summary: dict) -> list[dict]
run_evaluation(config, system_prompt, transcript, summary, timeout=120) -> dict
```

## 11. completeness_check.py — 完整性审计

**职责**：从议程覆盖、发言人覆盖、章节完整三个维度评估摘要是否完整。阈值 80%。

### 三个评估维度

| 维度 | 检查内容 | 计分 |
|------|---------|------|
| 议程覆盖 | 每个议程项在 discussion_points 中是否有对应议题 | covered / total |
| 发言人覆盖 | 每个实质性发言人在 discussion_points 中是否出现 | covered / total |
| 章节完整 | 7 个顶层章节中，有实质内容 vs 空 vs 缺失 | present / total |

### 综合覆盖率

```python
coverage_score = mean(agenda_coverage, speaker_coverage, section_coverage) * 100
passed = coverage_score >= 80.0
```

## 14. 提示词文件一览

| 文件 | 角色 | 输入 | 输出 |
|------|------|------|------|
| `summary_system.txt` | 摘要生成器 | 转录本（或合并事实） | 完整摘要 JSON |
| `semantic_split_system.txt` | 语义切分器 | 带编号的原文 | `[{title, start_sentence, end_sentence, summary}]` |
| `map_extract_system.txt` | 事实提取器 | 单个 chunk | `{chunk_id, facts: [...]}` |
| `verify_system.txt` | 事实校验器 | 原文 + 摘要 JSON | `{corrections, corrected_summary}` |
| `fact_check_system.txt` | 一致性审计 | 原文 + 声明列表 | `{verdicts: [{claim_id, verdict, reasoning}]}` |
| `action_items_system.txt` | 行动项提取器 | 原文 | `{action_items: [{id, task, assignee, ...}]}` |
| `completeness_system.txt` | 完整性审计 | 原文 + 摘要 | `{agenda_check, speaker_check, section_check}` |

### 提示词设计原则

1. **反幻觉规则为最高优先级**（`summary_system.txt`）：放在 prompt 最前面，要求每条附带 `source_quote` + `factual_confidence`
2. **Map 阶段禁止概括**（`map_extract_system.txt`）：只提取事实，用原文措辞，不做任何总结
3. **所有辅助提示词统一输出格式**：`Return ONLY a valid JSON object — no markdown fences`
